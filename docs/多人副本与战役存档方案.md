# 多队副本与四人战役存档方案

这是针对现有 Forge 1.20.1 僵尸模式的设计建议。0.2.24b 本次实现 NPC 姿态与持枪支援，不实现副本或战役存档系统。

## 同一关卡供多队同时游玩

图四描述的核心是“关卡模板”：建筑和部署规则编辑一次，生成房间时复用。它没有明确说明两队的世界如何隔离，所以它可以和临时维度、固定维度或同维度远距离复制结合。

| 方式 | 做法 | 适合程度 |
| --- | --- | --- |
| 同一维度的远处复制地图 | 预留多块远离的场地，向空闲位置复制模板；所有部署坐标加同一偏移 | 能较快落地，但全局时间、天气、其他模组事件和越界实体更难隔离 |
| 预建副本维度池 | 服务器启动时载入若干空维度；每队租用一个，放置模板并创建独立房间；结束后清理重置再回收 | 建议先采用，世界隔离清晰，避免运行中反复注册和卸载维度 |
| 动态创建并销毁维度 | 每次开房新建世界，退出后卸载、清理磁盘 | 可以作为后续方向；必须验证区块加载、存盘、客户端维度同步和其他模组缓存的完整生命周期 |

我的建议：先实现“关卡模板 + 固定副本维度池 + 每局独立实例”。两队玩同一关时，它们复用相同模板，拥有不同的实体、地图变化和剧情进度。模板文件不复制成多份独立维护。

Forge 将许多世界数据放在数据驱动的动态注册表中；这不等于提供完整的运行时房间创建/销毁服务。选择维度池是本项目的工程取舍。[Forge 1.20.1 注册表说明](https://docs.minecraftforge.net/en/1.20.1/concepts/registries/)

现有代码中房间以游戏类型和地图名标识，而地图坐标、NPC 与规则引用目前主要是绝对坐标。开始实现时要先拆开三个身份：

- `templateId`：部署者维护的关卡模板，例如“品学楼”。
- `instanceId`：本次运行的房间，不能只用模板名字。
- `campaignId`：正在推进的战役存档，与这次租到哪个副本维度无关。

模板以锚点保存相对位置，实例生成时统一转换：建筑、方块实体、刷怪点、屏障、购买点、出生点、NPC、地图事件、场景快照的目标位置和寻路数据都必须转换。已保存的场景快照本身可以直接复用，不需要重新读取模板源区域。规则引用使用稳定编号，不能靠实体 UUID 连接不同实例。

结束时依次锁定房间、保存战役检查点、传回玩家、取消延迟动作与枪械任务、移除实体和加载票据、恢复/重建地图、释放房间与导航缓存，最后归还维度。任何异步回调必须核对实例编号，避免上一局回调修改下一局。服务器异常退出后的恢复也必须有记录；销毁正在写入的世界文件不可作为正常清理流程。

不同维度仍在同一服务器中运行，不会因此自动获得多台服务器的算力；容量需要按地图大小、怪物数、NPC 枪战和实际服务器性能测量。

## 四人队伍的连续剧情

不要把四名玩家的 NPC 生死和任务状态合并成一份世界。一个 NPC 不可能同时既活着又死去。建议采用“战役存档拥有世界，玩家以成员或访客身份参加”。

创建战役时生成独立的 `campaignId`，记录管理者和允许加入的成员。开房时明确选择要继续的存档；队长只是这次组织队伍的人，存档所有权可以按约定转移，不必绑定唯一能在线的人。其他人加入时看到关卡、检查点、重要剧情差异，并确认使用该存档。

| 数据 | 归属与规则 |
| --- | --- |
| NPC 生死、支线阶段、阵营、地图变化、结局旗标 | 战役共享状态，本局四个人看到一致结果 |
| 剧情钥匙、信件、任务证物 | 战役物品；用任务物品编号和唯一实例编号管理，推荐队伍共享任务背包 |
| 普通枪械、弹药、治疗物品 | 按战役角色保存；与大厅和其他战役库存隔离 |
| 个人成就、看过的剧情、关卡解锁、外观 | 个人记录，可随访客游玩获得 |
| 结局 | 此次战役的共同结局；个人可记录“在某战役达成某结局”，不覆盖个人其他战役 |

例如 A 的存档里老人已经死亡，B 自己的存档里老人仍存活。B 加入 A 时看到的是老人死亡的世界；退出回到自己的存档，老人仍然活着。B 在 A 的战役获得的剧情钥匙不会被带进 B 的另一个战役。这样能更换队员，也不会靠跨存档搬运物品跳过剧情。

“上一关物品带到下一关”在同一个战役内正常保留。现有武器有房间归属数据，过关时应由服务器将合法装备重新绑定到新实例，不能直接沿用上一房间的标记。NPC 条件应检查战役任务物品/旗标，而不只检查某个玩家的普通背包。领取和交付要以原子操作更新共享任务状态，防止两个人同时领取导致复制、重复提交导致任务物品消失。需要保留实体物品演出时，物品携带 `campaignId` 与唯一编号，离队、死亡、背包满时回收至队伍任务背包。

新成员加入后使用自己的战役角色档；第一次来时使用当前检查点允许的装备模板，不继承被替换成员的私人背包。关键剧情选择由管理者确认或队伍投票，规则提前固定，避免四个人点击不同选项造成竞争。

## 保存与恢复的落地顺序

现有 NPC 规则完成状态是本局临时状态，应与长期任务旗标分开。只有明确声明为战役事件的支线选择、NPC 生死和任务阶段写入长期存档；波次等待、当前对话窗口、枪战目标与弹药计时不能简单全部永久化。

第一阶段只做安全检查点存档：关卡入口、篝火/安全屋、波次间休整、过关。保存战役与模板版本、当前关卡和检查点、已提交的任务旗标、共享任务物品、角色装备、NPC 持久状态和地图事件完成状态。

不建议第一版恢复到某一颗子弹飞到一半或某条延迟对话的中间；离线恢复从最近安全检查点开始，重建怪物、NPC 和剧情流程。暂停中的分支或对话不能随意标记完成，重入时应有明确入口。

之后再增加更细的波次检查点、断线重连保留时间、任务事件日志、自动备份与存档迁移。已发布模板升级时需要迁移旧旗标，不能因规则节点改名就直接清空玩家进度。

建议开发顺序：模板/实例身份拆分 → 两个固定副本维度验证隔离 → 检查点与战役共享任务背包 → 关卡间传送与物品延续 → NPC 持久支线与结局 → 更复杂的运行中恢复。
